# Multiplayer Foundation Plan

This is the first credible multiplayer shape for Aureus. The goal is not to staple sockets onto the current single-player app state. The goal is to split authority cleanly enough that a room server can own gameplay without dragging UI state and render internals into the network protocol.

## Why The Current Shape Is Single-Player

`GameState` currently mixes three different concerns into one serializable object:

- shared world truth such as time, weather, buildings, navigation zones, permits, NPCs, mines, and story flags
- player-owned progress such as money, ore, evidence, energy, meters, cooldowns, inventory, and position/path
- local UI state such as active overlays, selected permit/NPC/building, minigame visibility, and the current scene shell

That is fine for a local game. It is the wrong shape for multiplayer because two clients cannot safely co-author the same overlays, dialogue focus, or path state.

## New State Boundaries

The new state model in `src/multiplayer/types.ts` splits the world into:

- `RoomSharedState`: the room-level truth that should be broadcast to every participant
- `RoomPlayerState`: player-owned progress and movement state that the room server stores per player
- `ClientUiState`: local-only view state that should never become authoritative shared truth

`src/multiplayer/adapters.ts` provides a migration bridge between the old single-player `GameState` shape and the new `RoomSnapshot` shape so the refactor can happen incrementally instead of as a flag day rewrite.

## Authority Model

The room server should become authoritative for:

- world time and weather
- permit processing cadence
- movement resolution and exhaustion collapse
- travel into mines
- story-state mutations that affect the room

The client should remain responsible for:

- rendering
- animation smoothing
- local panel visibility and overlay UX
- intent submission

This keeps `VoxelEngine` and the React scene tree on the rendering side of the boundary instead of accidentally turning them into authoritative gameplay systems.

## First Extracted Server-Ready Systems

The first systems extracted out of React hooks are:

- `src/game/ticks/movementTick.ts`
- `src/game/ticks/timeTick.ts`

These are pure tick modules that take explicit runtime inputs and return:

- the next authoritative game state
- any ephemeral runtime state needed by the scheduler
- notifications generated by the tick

The existing browser hooks now call these tick functions, so current gameplay behavior stays intact while the same logic becomes reusable by a future room server.

## Current Client Bridge

The client now has a first room-session bridge in `src/hooks/app/useRoomSession.ts`.

Its job is deliberately modest right now:

- mirror the current local `GameState` into a `RoomSnapshot`
- preserve any remote players injected by a future transport layer
- derive renderer-friendly `RemotePlayerView` records for the world scene
- support eventual snapshot hydration back into `GameState`

This means the app can start routing through room-shaped data without forcing the networking layer to exist yet.

## Renderer Readiness

The world renderer no longer assumes there is only one visible player avatar.

- `EntityManager` now manages a `remotePlayers` collection alongside the local player and NPCs
- `VoxelWorldContainer` accepts `remotePlayers`
- `WorldScene` and `GameSceneRouter` forward remote player data through the render boundary

Single-player behavior is unchanged because the current room bridge produces an empty remote-player list unless external room data is merged in.

## Transport Layer

There is now a minimal real transport path:

- `scripts/multiplayer-server.ts` starts an in-memory WebSocket room server
- `src/hooks/app/useMultiplayerTransport.ts` connects the client to that server
- `src/multiplayer/protocol.ts` defines the wire messages
- `src/multiplayer/clientConfig.ts` resolves room, player, and server config from URL params and env

### Current operating model

This is intentionally conservative:

- the server is authoritative for the shared room clock (`day`, `time`, `weather`)
- the host client is authoritative for broader shared campaign state and pushes that state upstream
- every client pushes its own player state for presence, movement, and rendering
- remote players are rendered live in the world scene

That means this is a real multiplayer transport, but not yet a full command-authoritative simulation.

### How to run it

1. Start the room server with `npm run multiplayer:server`
2. Set `VITE_MULTIPLAYER_WS_URL` in `.env`
3. Open the client with query params such as `?room=test-room&player=Klaas`
4. Open a second browser/tab with the same `room` value and a different `player` value

The debug panel will show room status, peer count, and host/client role.

## Recommended Next Implementation Slices

1. Replace host-shared-state sync with explicit room commands for permits, city events, exports, travel, and mine interactions.
2. Move permit/city-event authority from the host client into the room server.
3. Decide which narrative systems are room-shared vs player-local before networking dialogue and endings.
4. Add snapshot sequencing / conflict protection so reconnects and stale host writes cannot roll shared state backward.

## Hard Rules

- Do not sync `GameState` wholesale over the wire.
- Do not make UI overlays shared room truth.
- Do not put gameplay authority into `VoxelEngine`.
- Do not let browser timer cadence define canonical multiplayer outcomes.
